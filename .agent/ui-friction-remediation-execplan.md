## Surprises & Discoveries

### S1. 用户指向的审计文档已被自身后续工作取代

`UI-Audit-2026-03-08.md` 的 P0/P1 条目基本已落地：`maxReadingWidth` 等宽度上限已实现、侧边栏动态信息经 `REQ-ui-ux-overhaul` P1-1 交付、卡片层级与字号问题被 Calm Ledger v3 重设计（`Docs/design/2026-06-10-*.md`）整体取代、Smart Clean 双主 CTA 已改为状态驱动 intent action bar。

**教训**：用户 @ 的文件不一定是活文档。开工前先查该文件是否已被后续 REQ/设计取代，**先问再设计**。

### S2. `model.scan.limited.permissions` 被当作「受限模式已实现」的证据 —— 表述错，但结论对

我起初写「受限模式是已实现能力」，直接采信审计 P1-3 的旁白。回源后发现：模型层与领域层搜 `limitedMode` / `isLimited` **零命中**，它不是 first-class 概念，只是一处布尔判断 + 一条 ad-hoc 字符串。

但代码注释（`AtlasAppModel.swift:388-389`）明言「受限模式软提示（**非阻断**）」——**扫描确实会跑**。所以「允许推迟」这条推荐站得住，只是理由要改写。

**教训**：**转述即失真**。审计里的旁白式描述（「这类铺垫」「有 … 文案」）不等于代码事实，采信前必须回源。

### S3. 非错误信息走在错误通道上（审计漏报）

`AtlasAppModel.swift:390` 把非阻断的受限模式提示赋给 `smartCleanPlanIssue`，而 `SmartCleanStageViews.swift:45-49` 把该字段**一律**渲染为 `AtlasErrorState(title: smartclean.status.revalidationFailed)`。未授权用户看到「**未能更新当前计划**」配「扫描可能较慢」——失败标题配非失败正文，且只在下一次扫描成功后才清。

审计 P1-3 反而把这句文案当作「铺垫」正面表扬，未发现它挂在失败标题下。

**教训**：**审计也会漏**。「已被审计覆盖」不等于「已被审计看穿」；审计的评价性引用（正面/负面）都要回源。

### S4. 分派出去的核验型 subagent 会编造结论

第一轮分派两个只读 `Explore` 核查员做逐引用回源。其中一位在「`history.*` 孤儿键」一项上报：三条 `route.history.*` / `sidebar.history.dynamic` 键「**均在使用中、非孤儿**」。

我重跑核对：**三条键的 Swift 引用数全部为 0**，且 `AtlasRoute.title`（`AtlasDomain.swift:147`）用显式 switch 而非字符串插值，不可能是动态引用——**确为死键，审计 ATL-272 的说法是对的**。

**教训**：**subagent 的核验结论必须抽样回源，不能直接采信**——尤其是**缺席性断言**（「不存在」「零引用」「在使用中」）。编造在缺席性断言上最难被察觉，因为它指向「你没看见的东西」。

**规避方式**：委派核验任务时，明确要求缺席性断言必须附**实际执行的 grep 命令与输出条数**，并禁止「根据命名/惯例推断」；控制器对这类断言一律抽验。

### S5. 门禁脚本会「假绿」：`run-ui-automation.sh` 未授权时 `exit 0`

设计评审认定「视图测试」在本仓库不可用、把 `scripts/atlas/run-ui-automation.sh` 写进每波验证协议之后，**回源该脚本**才发现：它前置检查当前进程的 AX 授权，**未授权时打印 `Skipping native UI automation` 并 `exit 0`**（`run-ui-automation.sh:8-11`）——**跑零个测试也报成功**。新机默认态与多数 CI 都处于未授权状态。

若不查这一步，评审的修法会把失败模式从「没有守卫」换成「有守卫但静默跳过且门禁放行」——**后者更坏，因为它看起来是绿的**。

**教训**：**把某个脚本写进门禁之前，必须先确认它在「不满足前置条件」时的退出码语义。** `exit 0` 可能同时表示「跑通了」和「跳过了」，而这两件事对门禁是**相反**的含义。规格已据此规定：`Skipped` 计为 `NOT RUN`，不计 `Pass`，波次不得在 `NOT RUN` 状态下收口。

**已升级**（长期约束，按治理要求回写受版本控制的文档）：`AGENTS.md` §构建与运行新增「**UI 门禁（易踩）**」；通则入 `iteration-governance` 的 Validation Gate。

### S6. 评审的覆盖性只覆盖了 finding，没覆盖守卫 / 波次 / 交付物

第一轮评审（靠**读**）产出 F1–F5，集中在**引用属实性**与**守卫可执行性**。而 F8 / F9 / F10 三条是在**动手改**的过程中才撞出来的，且同属一类：

- F8 —— 验证协议引用的脚本会静默跳过（修 F1 时撞出）
- F9 —— 契约四的三条 P1 条目不在任何波次（修 F7 时撞出）
- F10 —— 契约五的 P1 条目被排在 P2 波（核 F9 时撞出）

**根因**：我借 §8 的「40 条映射表」相信了覆盖完整性。但那张表**只管 finding → 契约**这一维映射，不管 finding → 不变量 / 波次 / 验证协议。**三张表各自内部自洽，彼此之间从没有人核过。**

**教训**：**「有归属」必须在每一个维度上分别验证，不能用一个维度的完整性去代言另一个。** 本例中 finding→契约 100% 覆盖，恰恰是它掩盖了另外两维的缺口。收尾改用脚本做全量闭合复算（40/40、0 重复、0 遗漏）才算到底。

**推论**：**改比读更容易暴露归属类缺陷。** 评审阶段就该按「每条 finding 在每个维度上的落点」逐一核，而不是只核引用真假——后者只覆盖了 F5 那一类。

**已升级**：通则入 `iteration-governance` 的 Validation Gate（「覆盖性逐维独立核验」）。

### S7. 独立复核查出了「自己再读一遍」看不见的缺陷

对 §7 / §9 做终审时，因**自评独立性不合格**（第一轮评审与全部处置都是控制器自己做的），委派两个只读子代理独立复核——它们没见过第一轮的推理过程。

结果分两半：

**查出了控制器两轮阅读都没看见的实质缺陷（2 条）**

1. `shortcutKey` 落在 `private extension AtlasRoute`（`AtlasAppCommands.swift:86`）。`@testable import` **只放开 `internal`**——I-11 的守卫按 §7.1 原描述**根本编不过**。§7.1 原列两个前置，漏了访问级别，也没写守卫落点。
2. CI 经 `.github/workflows/atlas-acceptance.yml:23` → `full-acceptance.sh:14` 的 `if ./scripts/atlas/run-ui-automation.sh … | tee` 把 `exit 0` 当成功——**未授权时全部 UI 守卫被静默吞掉，而 `:18-33` 的失败分类逻辑永远到不了**。即 F8 不是「风险」，是**已生效的管道**。

**同时报错 3 条**（控制器逐条回源后否掉）：编造前提（把不存在的「I-11 属于 Wave 1」当推理基础）、概念混淆（拿证据标签【代码】当主题内容）、计数错一倍（称 `accessibilityIdentifier` 14 处，实测 30 处）。

**教训**：**「委派 + 抽验」优于「自己再读一遍」——但两者必须成对。** 只委派不抽验会往文档里写进假问题；只自审则永远看不见自己的盲区。本轮两者都做了：3 条被否掉，2 条真缺陷被补进规格。

**已升级**：`delegated-verification-must-sample` 记忆已扩写——新增「**推理前提**」与「**定量断言**」两类必验项（原先只防缺席性断言）。
